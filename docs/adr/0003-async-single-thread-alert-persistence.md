# 0003. 경보 저장을 단일 스레드 비동기로 분리

- 날짜: 2026-08-05
- 상태: 채택

## 배경

로봇이 보낸 화재·과열 경보는 WebSocket 수신 스레드에서 곧바로 DB에 저장되고 있었습니다. 저장이 늦어지면 같은 스레드가 처리하던 텔레메트리와 영상 프레임 수신까지 밀립니다. 개발 환경은 SQLite 커넥션 1개라 경합이 생기기 쉬웠습니다.

백엔드 로직을 전수 점검하다가 이 구조를 발견했습니다.

## 고려한 선택지

1. **스레드 풀 비동기(여러 스레드)**: 처리량은 늘지만 경보 저장 순서가 바뀔 수 있습니다. 중복 판정(같은 로봇·같은 종류 경보를 10분 동안 억제)이 순서에 의존해서, 순서가 바뀌면 판정이 흔들립니다.
2. **메시지 큐(Kafka 등) 도입**: 순서와 내구성은 확실하지만 이 규모에서는 운영 부담이 큽니다.
3. **단일 스레드 비동기 executor**: 수신 스레드에서는 떼어 내되, 저장은 한 줄로 처리해 순서를 지킵니다.

## 결정

3번을 택했습니다. 경보 저장 리스너에 `@Async`를 붙이고 전용 executor를 둡니다.

- core/max 스레드 1개, 대기열 200건
- 대기열이 차면 `CallerRunsPolicy`: 호출한 스레드가 직접 처리합니다. 경보를 버리지 않고 수신 속도를 늦추는 쪽을 택했습니다.

## 결과

- 얻은 것: 수신 스레드가 DB를 기다리지 않음. 경보 순서와 중복 판정 순서가 유지됨. 과부하 때 유실 대신 역압.
- 치른 대가: 처리량의 상한이 스레드 하나입니다. 로봇이 늘면 로봇별로 나눈 큐(키 기준 분할)가 필요합니다.
- 같은 점검에서 함께 고친 것: 재접속할 때 옛 세션이 새 세션 매핑을 지우던 문제, 경보 좌표 (0, 0) 고정, 공개된 기본 시크릿, 중복 판정 맵이 계속 커지던 문제 등 모두 8건.
