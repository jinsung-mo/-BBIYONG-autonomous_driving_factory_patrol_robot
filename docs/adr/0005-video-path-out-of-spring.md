# 0005. 영상을 Spring 밖(MediaMTX, WebRTC)으로

- 날짜: 2026-08-13 (HLS 전환 8/12, WebRTC 전환 8/13)
- 상태: 채택

## 배경

처음에는 로봇이 JPEG 프레임을 base64로 WebSocket에 실어 보내고, Spring이 STOMP로 관제 화면마다 복사해 보냈습니다.

- 보는 사람이 늘수록 서버 송신량이 그만큼 늘었습니다.
- 느린 브라우저 하나가 송신 버퍼를 채우면 세션이 끊겼습니다. 버퍼 초과 끊김은 3시간에 20번에서 5분에 7번까지 늘었습니다.
- 서버가 경보·상태 처리와 영상 복사를 같은 프로세스에서 하고 있었습니다.

## 고려한 선택지

1. **STOMP 버퍼를 계속 키우기**: 끊김은 줄지만 느린 구독자에게 낡은 프레임이 쌓이고 메모리 사용이 늘어납니다.
2. **HLS(nginx 정적 서빙)**: 서버 부담은 사라지지만 2초 세그먼트 구조 때문에 지연이 6초쯤 됩니다. 화재 알림은 바로 오는데 영상은 6초 뒤에 보이고, 원격 조종은 할 수 없습니다.
3. **WebRTC(WHEP) + 미디어 서버(MediaMTX)**: 로봇이 H.264로 한 번 인코딩해 SRT로 올리고, 브라우저가 WebRTC로 받습니다.

## 결정

HLS를 거쳐(8/12) 최종적으로 3번으로 옮겼습니다(8/13). HLS는 폴백으로 남겼습니다.

영상이 STOMP를 떠난 뒤 STOMP 송신 버퍼는 4MB에서 512KB로 줄였습니다. 남은 데이터가 초당 수십 KB뿐이라 큰 버퍼는 몇 초 전 지도와 온도를 쌓아 두기만 했기 때문입니다. 영상이 빠지기 전에 줄이면 끊김이 더 잦아지므로, 로봇 쪽 전환 로그를 확인한 다음에 줄였습니다.

## 결과

- 얻은 것: Spring이 영상 바이트를 다루지 않음. 로봇 송신량 12.3Mbps → 8.2Mbps(HLS 전환 시점 실측). 영상 지연 약 6초 → 0.3초 안팎(관제 화면 보정값 기준).
- 치른 대가: 미디어 서버라는 구성 요소가 하나 늘었습니다. WebRTC용 UDP 포트(8189)도 열어야 합니다.
- 제 몫: 영상 경로는 팀과 함께 바꿨고, 저는 관제 화면을 WebRTC로 바꾸고 탐지 박스와 영상의 시간 보정을 맞추는 작업을 맡았습니다.
