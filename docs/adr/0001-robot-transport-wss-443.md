# 0001. 로봇 통신을 TCP 9000에서 Nginx 경유 WSS 443으로

- 날짜: 2026-07-22
- 상태: 채택

## 배경

로봇(Jetson Orin Nano)과 관제 서버(AWS EC2)가 상태, 명령, 경보를 주고받을 연결이 필요했습니다. 처음에는 TCP 9000번 포트에 JSON 한 줄씩 보내는 서버를 만들었습니다(7/21).

배포 서버를 확인해 보니 방화벽(ufw)이 22, 80, 443, 8989번만 열어 두고 9000번을 막고 있었습니다. 로봇이 붙을 수 있는 망(교육장 내부망, LTE, 공장 망)도 대개 임의 포트를 막습니다. 무선 구간으로 제어 명령(`cmd_vel`)이 평문으로 오가는 것도 문제였습니다.

## 고려한 선택지

1. **방화벽에 9000번 개방**: 가장 빠르지만 현장 망마다 다시 요청해야 하고 암호화가 없습니다.
2. **MQTT 브로커**: Pub/Sub에는 잘 맞지만 브로커를 따로 운영해야 합니다. 당시 서버 후보였던 라즈베리파이 5에서는 부담이었고 개발 기간은 4주였습니다.
3. **Nginx를 거치는 WebSocket(WSS, 443)**: 표준 포트라 방화벽을 그대로 통과하고, TLS는 Nginx가 끝냅니다.

## 결정

3번을 택했습니다. 로봇은 `wss://<도메인>/ws/robot`으로 붙고, Nginx가 TLS를 풀어 Spring의 WebSocket 핸들러로 넘깁니다. 관제 웹은 같은 443 포트에서 STOMP(`/ws/control`)를 씁니다.

메시지 형식(JSON 필드)은 그대로 두고 전송 방식만 바꿨습니다. 로봇 쪽은 소켓 클라이언트만 WebSocket 클라이언트로 바꾸면 됐습니다.

## 결과

- 얻은 것: 방화벽 설정 변경 없이 연결. 제어 명령과 경보가 TLS로 암호화됨. 인증서와 라우팅을 Nginx 한 곳에서 관리.
- 치른 대가: 연결마다 HTTP 업그레이드 과정이 붙고, Nginx 설정(업그레이드 헤더, 타임아웃)을 따로 챙겨야 합니다.
- 뒤따른 일: 로봇 채널에 인증이 없다는 점이 나중에 드러나 핸드셰이크 토큰(`X-Robot-Token`)을 추가했습니다.
