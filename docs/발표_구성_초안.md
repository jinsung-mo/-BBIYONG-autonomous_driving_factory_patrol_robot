## 0. 확인 필요 사항 — 기획발표 vs 현재 리포지토리 불일치

기획발표 스크립트와 현재 코드베이스(FE/docs)를 대조하니 몇 가지 확정이 필요한 지점이 있습니다. **최종발표 전에 팀 내 확인 후 슬라이드에 정확한 내용으로 반영하세요** — 심사에서 발표 내용과 실물이 다르면 산출물 신뢰도가 크게 깎입니다.

| 항목 | 기획발표 내용 | 현재 리포지토리 확인 결과 | 확인 필요 |
| --- | --- | --- | --- |
| DB | MySQL | `architecture_and_api_spec.md`엔 SQLite로 명시 | 최종적으로 어떤 DB를 쓰는지 확정 |
| 대시보드 화면 구성 | "로봇 페이지" + "CCTV 페이지" 2분할 | 현재 FE 코드는 관제(RobotPage) / 운영(OpsPage) / 설정(ConfigPage) 3섹션 구조, 별도 CCTV 페이지 미확인 | 화면 명칭·구성이 바뀌었는지, 발표 자료 용어를 현재 화면에 맞게 갱신 |
| 인프라 | Nginx 리버스 프록시 + Jenkins CI/CD 배포 파이프라인 | 저장소 내에서 Nginx/Jenkins 설정 파일 미확인(BE_system은 Gradle 스켈레톤 수준) | 실제 구축 여부 확인 — 되어 있다면 산출물 슬라이드의 강력한 근거이므로 꼭 챙길 것 |
| BE_system 컨트롤러 | (기획 시점) 언급 없음 | 여전히 애플리케이션 스켈레톤만 존재, 컨트롤러 미구현 | 기획발표 이후 실제 진행 상황 최신화 |

## 1. 기획발표에서 재사용할 핵심 자산 (이미 검증된 스토리텔링)

이 요소들은 기획발표에서 이미 청중의 반응을 확인한 자산입니다. 최종발표에서 버리지 말고, 압축해서 재사용하세요.

- **훅 인용문**: "경보는 울렸지만, CCTV로 불이 확인되지 않아 당연히 오작동인 줄 알았습니다" (23:27, 박정호) / "결국 저의 실수로 공장 전체를 잃었습니다" (03:20)
- **통계**: 5년간 공장화재 61명 사망, 연평균 3,600억 원 손실 / 발화요인 1위 전기적 요인 28.1%, 그중 미확인 단락(합선) 39.6%
- **3대 감시 공백**: 지켜볼 사람이 없다 · 카메라가 못 보는 곳이 있다 · 경보가 울려도 믿지 않는다
- **컨셉 한 줄**: "돌아다니며 스스로 확인하는 순찰자"
- **7대 기능(3단계 흐름)**: 발견 DISCOVER(자율주행 순찰·화재연기감지·장비과열모니터링) → 확인 VERIFY(긴급출동제어·화재이중판정) → 알림 ALERT(과열자동경보·통합관제대시보드)
- **특장점 3가지**: 사각지대 제로화 / 이중판정 오탐차단 / 혼합형 운영(순찰↔긴급 전환)
- **FSM 6단계**: PATROL → DETECT → COMMAND → DISPATCH → VERIFY → RESUME (긴급 > 순찰 우선순위)
- **수동조작 4단계**: TAKEOVER → TELEOP → INSPECT → AUTO RESUME
- **백업 시연자료**: Appendix A(3D 시뮬레이션 핵심 장면), Appendix B(관제 대시보드 핵심 화면) — 최종발표에서도 동일하게 백업용으로 준비

> 톤 전환 원칙: "~할 계획입니다 / ~하도록 설계했습니다" → **"~하도록 구현했습니다 / 지금 보여드리겠습니다"** 로 전부 바꾼다. 심사위원은 이미 기획을 들었으므로, 최종발표의 가치는 "그게 진짜 됐는가"에 있다.

| ① 영상 포트폴리오 | 2:00 | 훅+통계를 15초로 압축 → "그래서 만들었습니다" → 실제 동작 화면 하이라이트 | 창의성(스토리텔링), 사용성(예고) |

## 3. 세그먼트별 상세

### ① 영상 포트폴리오 (2분)

| 컷 | 시간 | 내용 |
| --- | --- | --- |
| 1 | 0~15초 | 훅 압축 — 23:27 무인시간대 인용문을 자막으로 빠르게 (기획발표처럼 1분간 머물지 않는다) |
| 2 | 15~30초 | "삐용" 로고 + 한 줄 컨셉("돌아다니며 스스로 확인하는 순찰자") |
| 3 | 30~70초 | **실제 동작 화면** 하이라이트 — 3D 순찰맵, 화재 발생→출동 전환, 관제 대시보드 알림 팝업, 이벤트 로그 (빠른 컷 편집) |
| 4 | 70~95초 | 수동조작(WASD) 실사용 장면 |
| 5 | 95~110초 | 팀 소개(팀장 모진성 · 팀원 고지혁·박재현·이승현·이예승·장효준) |
| 6 | 110~120초 | 클로징 로고 + 발표자 등장 전환 자막 |

- 기획발표 훅은 "천천히 머무는" 연출이었지만, 최종발표 영상은 **빠른 임팩트** 위주로 편집(이미 알려진 문제이므로).
- 컷 3이 핵심 — 기획발표에는 없던 "진짜 동작하는 화면"을 여기서 처음 보여줘 임팩트를 만든다.

### ② PPT 발표① — 사전 설명 (4분)

| 슬라이드 | 시간 | 내용 | 평가축 |
| --- | --- | --- | --- |
| 1. 문제 요약 | 0:30 | "무인 시간대 감시 공백" 한 문장 요약 슬라이드(3대 공백 아이콘만, 통계 재설명 생략) | 실용성 |
| 2. 컨셉·차별점 | 1:00 | "돌아다니며 스스로 확인하는 순찰자" + 특장점 3가지(사각지대 제로화·이중판정 오탐차단·혼합형 운영)를 **완료형**으로 제시 | 창의성 |
| 3. 완성된 아키텍처 | 2:00 | 실제 구축한 시스템 구조(Nginx→React/관제서버, 관제서버↔DB, 관제서버↔로봇 WSS, CI/CD 파이프라인 포함) — 기획발표의 다이어그램을 "완성본"으로 갱신해서 제시 | 산출물 |
| 4. 시연 예고 | 0:30 | "지금부터 실제로 동작하는 모습을 직접 보여드리겠습니다" | - |

### ③ 시연 (4분) — 실제 제품 시연

기획발표의 시연 ①②를 그대로 순서 유지하되, "시뮬레이션"이 아니라 "완성된 산출물"로 프레이밍.

| 시연 | 시간 | 보여줄 것 | 사용성 강조 포인트 |
| --- | --- | --- | --- |
| ① 3D 순찰 시뮬레이션 | 2:00 | 순찰 모드 자율주행 → 화재 발견 → A* 최단경로로 긴급 출동 → 근접 확인(비전×열화상 이중판정) → 가장 가까운 지점으로 복귀 | 모드 전환이 즉각적이고 직관적으로 보이는가 |
| ② React 관제 대시보드 | 2:00 | 로그인 → 로봇 페이지(실시간 위치·모드, 수동 출동 지시) → 이벤트 로그(달력 기반 조회, 신뢰도 추이) | 실시간 갱신 속도, 알림 UI 자동 전환, 정보 가독성 |

- 시연 실패 대비: Appendix A(3D 백업 캡처) / Appendix B(대시보드 백업 캡처) 그대로 재사용 가능하게 준비.
- 라이브 서버 연결이 불안하면 mock 모드로 전환해 시연 — FE에 이미 mock/live 전환 기능이 있으므로 발표 리스크를 낮출 수 있음.

### ④ PPT 발표② — 마무리 (2분)

시간이 가장 촉박한 구간. 슬라이드 2~3장 이내로 압축.

| 슬라이드 | 시간 | 내용 | 평가축 |
| --- | --- | --- | --- |
| 1. 창의성·실용성 요약 | 0:45 | 7대 기능 3단계 흐름(발견→확인→알림)과 FSM 6단계를 한 장으로, "혼합형 상시 순찰"이 기존 CCTV/무인경비/단일센서 대비 무엇을 해결했는지 한 줄씩 대비 | 창의성, 실용성 |
| 2. 산출물 완성도 | 0:45 | 기술스택 요약(FE React+Vite+WebSocket, BE, 로봇 ROS2/Nav2), CI/CD·배포 현황(0번 항목 확인 후 기재), Jira/Git 협업 이력(Epic-Story-Task, 커밋-티켓 연동) | 산출물 |
| 3. 클로징 | 0:30 | 한 줄 요약("사람이 없는 시간에, CCTV가 못 보는 곳을 삐용이 순찰합니다") + 팀 소개 + Q&A 유도 | - |
