# 삐용 (BBIYONG) - Git 브랜치 전략 및 실무 가이드 (Git Branch Strategy & Workflow Guide)

본 문서는 팀 E101의 일관성 있고 안정적인 소스 코드 통합을 위한 Git 브랜치 운용 방식과 상세 실무 작업 흐름을 정의합니다. 모든 팀원은 본 가이드라인에 따라 깃 작업을 진행해 주시기 바랍니다.

---

## 1. Git 브랜치 구조 및 전략

팀 E101은 파트별 독립적인 개발 공간을 보장하고 메인 배포 브랜치(`main`)의 안정성을 극대화하기 위해 **파트별 메인 브랜치 체제**를 활용합니다.

```
                  ┌── fe/main ─────── (프론트엔드 메인)
                  ├── be_system/main ── (시스템 백엔드 메인)
[main] (배포용) ──┼── be_robot/main ─── (로봇 백엔드 메인)
                  └── ai/main ──────── (AI 파트 메인)
```

* **`main` (최종 통합 배포 브랜치)**: 스프린트 완료 또는 실배포 시점에 각 파트의 `*/main` 브랜치를 최종 병합하는 브랜치입니다. 직접 Push 및 머지가 제한되는 보호 브랜치입니다.
* **`*/main` (파트별 공통 메인 브랜치)**: 각 개발 파트(FE, BE, AI)의 팀원들이 코드를 최종 병합하는 공통 작업 기준 브랜치입니다.
* **기능 개발 브랜치**: 개별 기능 및 태스크를 개발하기 위해 파트 메인 브랜치에서 분기하여 생성하는 작업 브랜치입니다.

---

## 2. 기능 개발 브랜치 생성 규칙

모든 개별 작업은 반드시 지라(Jira) 티켓과 매핑되도록 브랜치 이름을 생성해야 합니다.

### 2.1 브랜치 명명 컨벤션
* **형식**: `[접두사]/[Jira티켓번호]-[간단한작업명]`
* **주요 접두사(Prefix)**:
  * `feat`: 새로운 기능 구현 및 개발 (예: `feat/S15P11E101-144-login`)
  * `fix`: 버그 및 오동작 수정 (예: `fix/S15P11E101-145-socket-error`)
  * `docs`: 문서 작성 및 보완 (예: `docs/S15P11E101-146-readme`)
  * `design`: UI 퍼블리싱 및 퍼포먼스 마크업 (예: `design/S15P11E101-147-map-ui`)
  * `refactor`: 가독성 및 성능 개선 등 구조 변경 (예: `refactor/S15P11E101-148-async`)
  * `chore`: 빌드, 인프라, 단순 라이브러리 추가 설정 (예: `chore/S15P11E101-149-jpa-config`)
  * `test`: 테스트 코드 작성 및 검증 (예: `test/S15P11E101-150-unit-test`)

## 3. 실무 Git 작업 흐름 (Step-by-Step)

개발 작업을 시작하고 완료하기까지의 표준 깃 워크플로우 6단계입니다.

### 1단계: 파트 메인 브랜치 최신화
새로운 브랜치를 생성하기 전에, 로컬의 파트 메인 브랜치로 이동하여 원격 저장소의 최신 변경 내용을 다운로드합니다.
*(예시: 시스템 백엔드 파트원인 경우 `be_system/main` 기준)*
```bash
# 1. 파트 메인 브랜치로 이동
git checkout be_system/main

# 2. 최신 코드 가져오기
git pull origin be_system/main
```

### 2단계: 기능 개발 브랜치 생성 및 이동
최신화된 파트 메인 브랜치를 기준으로 새 작업 브랜치를 만들고 이동합니다.
```bash
# 지라 티켓 번호를 포함해 명명
git checkout -b feat/S15P11E101-144-login
```

### 3단계: 커밋 및 작업 진행 (Jira 티켓 연동)
코드를 수정하고 커밋을 생성합니다. Jira 티켓에 해당 커밋과 코드가 자동으로 연동되도록 **커밋 메시지 맨 앞에 대괄호로 Jira 티켓 번호**를 남겨야 합니다.
* **커밋 메시지 서식**: `[Jira티켓번호] 접두사: [모듈] 작업 내용 요약`
```bash
# 1. 수정한 파일 스테이징
git add .

# 2. 지라 연동 규칙에 맞춰 커밋
git commit -m "[S15P11E101-144] feat: [BE] 회원가입 API 구현"
```

### 4단계: 원격 저장소 푸시
로컬 작업을 마치면 기능 개발 브랜치를 원격(GitLab)에 푸시합니다.
```bash
git push origin feat/S15P11E101-144-login
```

### 5단계: GitLab에서 Merge Request(MR) 생성 및 병합
1. GitLab 저장소에 접속하여 푸시된 브랜치 오른쪽에 나타나는 **`Create merge request`** 버튼을 누릅니다.
2. **Target 브랜치 설정에 주의해 주세요**:
   * **Source Branch**: `feat/S15P11E101-144-login`
   * **Target Branch**: **`be_system/main`** (최종 통합 브랜치인 `main`이 아닌, 본인 파트의 공통 브랜치로 보냅니다.)
3. 자동으로 뜨는 템플릿(개요, 작업 상세 내용, 완료 기준 및 테스트 결과)을 채워 넣고 생성합니다.
4. 파트원들의 리뷰와 승인을 얻은 뒤 **`Merge`** 버튼을 클릭하여 병합을 완료합니다.

### 6단계: 로컬 환경 정리 및 최신화
병합이 완료되면 로컬 PC에서 예전 작업 브랜치를 정리하고 다시 최신 상태로 유지합니다.
```bash
# 1. 파트 메인 브랜치로 복귀
git checkout be_system/main

# 2. 병합된 최신 코드 가져오기
git pull origin be_system/main

# 3. 로컬에서 다 쓴 작업 브랜치 삭제
git branch -d feat/S15P11E101-144-login

# 4. 원격에서 병합 후 삭제된 찌꺼기 브랜치 정보 로컬에서 정리
git fetch -p
```

## 4. 자주 발생하는 상황별 Git 팁 및 문제 해결

### 💡 실수로 커밋 메시지를 잘못 적었을 때
가장 최근에 작성한 커밋 메시지의 내용을 수정하고 싶다면 아래 명령어로 수정 창을 띄울 수 있습니다.
```bash
git commit --amend
```
*이미 원격 저장소에 푸시(`git push`)를 한 후에 수정했다면 수정 후 `git push origin <브랜치명> --force`로 강제 업데이트가 필요합니다. (주의해서 사용해 주세요)*

### 💡 임시로 작업을 멈추고 다른 브랜치로 전환해야 할 때
작업을 완수하지 못해 커밋하기 애매한 상황에서 급히 다른 브랜치로 가야 할 경우, 수정 중인 코드를 임시 저장소에 보관해 둘 수 있습니다.
```bash
# 1. 수정 중인 코드 임시 보관
git stash

# 2. 다른 브랜치로 전환해서 작업 가능
git checkout be_system/main

# 3. 다시 내 작업 브랜치로 돌아와 임시 저장했던 코드 꺼내기
git checkout feat/S15P11E101-144-login
git stash pop
```

### 💡 원격 저장소(GitLab)에 삭제된 브랜치가 계속 조회될 때
웹페이지에서 머지 완료되어 지워진 브랜치가 로컬 터미널에서 계속 조회된다면, 다음 명령어로 원격 서버의 실시간 동기화 상태를 가져와 찌꺼기 목록을 제거할 수 있습니다.
```bash
git fetch -p
```

### 💡 타 파트의 최신 연동 코드(최종 main)가 내 개발 브랜치에 필요할 때 (안전한 3단계 동기화)
기능 개발 중에 프론트엔드나 타 백엔드 개발자 등이 최종 `main`에 머지한 최신 코드가 내 로컬 환경에 연동을 위해 필요한 경우가 있습니다. 

이때, 내 기능 브랜치(`feat/S15P11E101-144-login`) 안에서 바로 `git pull origin main`을 실행하면 **절대 안 됩니다.** 
* **이유**: 내 기능 브랜치는 나중에 `be_system/main`으로 머지되어야 합니다. 여기에 `main`을 직접 부어버리면, `be_system/main`에 존재하지 않는 타 파트(프론트, AI 등)의 대량 코드가 내 브랜치에 유입됩니다. 이 상태로 MR을 생성하면 **내가 짜지 않은 남의 코드까지 내 MR의 변경 이력(Diff)에 섞여 나와 코드 리뷰가 불가능**해집니다.

이를 방지하기 위한 **가장 안전한 3단계 동기화 실무 워크플로우**입니다:

#### 1단계: 내 파트 메인 브랜치로 이동 및 최신화
우선 내 파트 메인 브랜치(`be_system/main`)로 이동한 후, 원격의 파트 메인 코드를 pull 받습니다.
```bash
git checkout be_system/main
git pull origin be_system/main
```

#### 2단계: 최종 배포 브랜치(main)의 코드를 내 파트 메인에 병합
원격의 최종 `main` 변경분을 백엔드 파트 공통 메인 브랜치(`be_system/main`)에 합쳐 공통 기준을 최신화합니다.
```bash
git pull origin main
```

#### 3단계: 내 작업 브랜치로 이동 후, 최신화된 파트 메인을 내 브랜치에 병합
최종 `main`까지 모두 수용된 우주 최신 상태의 파트 메인(`be_system/main`)을 내 작업 브랜치에 merge해 줍니다.
```bash
git checkout feat/S15P11E101-144-login
git merge be_system/main
```
이렇게 하면 내 로컬에서 안전하게 충돌을 해결할 수 있으며, 나중에 GitLab에 올렸을 때도 **정확히 내 로그인 코드만 깔끔하게 변경 이력(Diff)에 남아** 리뷰받기 매우 편해집니다.
