# 관제 프로토콜 확장 제안 (레인 B → 레인 A)

작성 2026-08-12 · 근거 당일 라이브 실측 · 대상 `docs/설계_2026-08-12_무인사이클_기동설계.md` §08·§09

레인 B(관제)가 진행하려면 **WebSocket 메시지 계약 5건**이 정해져야 한다. 규약대로 각 항목에
버린 대안까지 적었다. **각 항목은 독립이므로 따로 승인·거절할 수 있다.**

> 왜 지금인가 — 재설계 노트 §10은 "단계 가시성 + 실패 알림"을 **순서 7**(마지막)에 두었다.
> 그런데 그 둘이 레인 B 남은 일의 대부분이고 둘 다 계약이 선행이다. 순서 7까지 기다리면
> 레인 A가 1~5를 하는 동안 레인 B가 놀게 된다. **합의 자체는 싸다**(문자열 목록 하나,
> 필드 세 개) — 제안을 먼저 통과시키고 구현은 §10 순서대로 가면 두 레인이 병렬로 돈다.
> 이것이 이 문서가 요청하는 유일한 순서 변경이다.

## 1. `status` 값 집합 확정

### 무엇을
로봇이 단계 전이 시 `TELEMETRY.status` 에 아래 값 중 하나를 보낸다.

```
BOOT · READY · MAPPING · SAVING · LOCALIZING
AUTO_PATROL · APPROACH · VERIFY · EVENT · DEGRADED · MANUAL_CONTROL
```

재설계 노트 §03 그림 3의 상태 기계와 1:1로 맞췄다.

### 왜
지금 로봇이 보내는 값은 **`MAPPING`·`AUTO_PATROL` 둘뿐**이고 나머지 단계는 필드 자체가
생략된다(§08). 결과:

- 부팅·스택 기동 중이 **"연결 끊김"으로만** 보인다 — 브리지가 아직 없으니 관제는 구분할 수 없다
- 지도 저장·위치추정 전환이 **`MAPPING` 한 값으로 뭉개진다**
- 화재 접근·확인 단계가 안 보인다

무인 사이클에서 "지금 어느 단계인가"가 관제에 안 보이면, 조작자는 멈춘 것과 진행 중인 것을
구별할 수 없다.

### 🔑 서버 변경이 필요 없다
`RobotPacket.status` 는 이미 `private String status;` 다 — 임의 문자열을 통과시킨다.
**로봇이 보내기만 하면 서버는 그대로 중계한다.**

### FE 쪽 처리
모르는 값이 오면 **원문을 그대로 표시**한다. 그래서 로봇이 나중에 붙어도, 또 목록에 없는 새
값을 추가해도 화면이 깨지지 않는다. 이 방식은 `readiness.blockedBy` 가 이미 쓰고 있는 선례다
— *"로봇이 표에 없는 새 사유를 추가해도 역직렬화가 깨지면 안 된다"*.

### 버린 대안
- **(a) Java `enum` 으로 못 박기** — 로봇이 새 단계를 추가하는 순간 역직렬화가 깨진다.
  `RobotPacket` 주석이 이미 같은 이유로 열거형을 피하라고 적고 있다.
- **(b) `stage` 라는 새 필드 신설** — `status` 와 의미가 겹쳐 둘 중 무엇이 정본인지 모호해진다.
  필드를 늘리지 않고 기존 필드의 값 집합만 넓히는 쪽이 싸다.

## 2. `EVENT_SYSTEM` 을 알림 경로에 올린다

### 무엇을
1. 로봇이 **부팅 실패 · 순찰 관문 실패 · 위치추정 전환 실패**를 `EVENT_SYSTEM` 으로 보낸다
   (기존 `code`·`message` 필드 사용, 신규 필드 없음)
2. 서버가 `EVENT_SYSTEM` 을 `/topic/alerts` 로 **방송**한다
3. `severity` 를 붙여 화재와 **등급을 분리**한다 — 제안: `CRITICAL | WARN | INFO`

### 왜
§08 "알림 공백": 실패를 사람에게 알리는 경로가 **화재·과열뿐**이다. `EVENT_SYSTEM`(planner
사망 등)은 서버가 방송하지 않고 알림 서비스도 안 타서 이벤트 목록에 INFO 로만 남는다. 그리고
부팅 실패·관문 실패·위치추정 실패는 **클라우드로 나가는 경로가 아예 없다.**

무인 운전에서 이건 "고장이 나도 아무도 모른다"는 뜻이다. 실제로 오늘 다섯 건 중 다섯 건이
**화면에 오류가 없는데 동작이 틀린** 형태였다(§01).

### 왜 등급을 나누나
등급 없이 `/topic/alerts` 에 합치면 시스템 경고가 화재 알림과 같은 무게로 뜬다. 조작자가
곧 **화재 알림 자체를 무시하게 된다** — 이건 알림을 늘리는 게 아니라 없애는 결과다.

### 버린 대안
- **(a) `EVENT_FIRE` 로 재사용** — 화재 경보에 시스템 오류가 섞인다. 위 이유로 최악이다.
- **(b) 별도 토픽 `/topic/system` 신설** — FE 가 구독을 하나 더 유지해야 하고, 알림 UI 가 두
  경로로 갈려 "무엇이 최신 경보인가"를 두 곳에서 합쳐야 한다. 등급 필드 하나가 더 싸다.

## 3. 🔴 검출 박스 전달 방식 — **A/B 택1이 필요하다**

이 문서에서 유일하게 진짜 설계 선택이다.

### 현재 상태 (실측)
- 로봇이 박스를 **400×300 미리보기 JPEG 픽셀에 태워** 보낸다
- `cam.json` 에는 `dets`·`src_w`·`src_h` 가 **이미 있다** — 그런데 `VIDEO_FRAME` 에는 없다
- 🔴 실측: `src_w=640` (추론 프레임), 영상 폭 **1280** → **좌표 기준이 2배 어긋난다**

### 안 A — `VIDEO_FRAME` 에 `dets` + `src_w/src_h` 추가
재설계 노트 §09 권장안.

### 안 B — 별도 저주기 메시지 `DETECTIONS` — **권장**
`{type:"DETECTIONS", robot_id, src_w, src_h, dets:[…], captureTs}` 를 탐지 주기로 보낸다.

### 왜 B 를 권하나
- **주기가 다르다.** 탐지는 `DET_HZ=4`, 영상 송신은 5fps. 프레임마다 실으면 같은 박스를
  중복 전송하거나, 반대로 박스가 영상 프레임을 기다려야 한다.
- **크기 차이가 극단적이다.** 프레임은 134KB(base64), 박스는 수백 바이트다. 묶으면 박스만
  필요한 소비자도 영상 대역폭을 함께 물어야 한다.
- **영상 전송률을 바꿔도 탐지가 안 흔들린다.** 오늘 송신을 15→5fps 로 줄였는데, 묶여 있었다면
  박스 갱신률도 같이 떨어졌을 것이다.

### 버린 대안
- **(c) 현행 유지 — 로봇이 픽셀에 태운다** — 미리보기가 400×300 이라 박스 해상도가 거기 묶인다.
  FE 가 박스를 끄거나 색·굵기를 바꿀 수 없고, 박스와 영상을 따로 확대할 수도 없다.
- **(d) FE 가 `src_w` 없이 영상 크기로 나눈다** — 지금 상태에서 2배 어긋난다. `src_w` 를
  안 쓰면 해상도를 바꿀 때마다 조용히 틀린다. 실제로 *"대시보드가 박스를 1.6배 어긋나게
  그렸다"* 는 기록이 `camera_node.py` 주석에 남아 있다.

## 4. `inferenceFps` → `inferenceMs`

### 무엇을
필드를 `inferenceMs`(1회 추론 소요시간, ms)로 개명한다. 로봇은 **역수를 취하지 않고 그대로**
보낸다.

### 왜 — 지금 관제가 거짓을 표시하고 있다
실측 `cam.json`: `det_fps: 92.7`. 그런데 `camera_node` 의 계산은

```python
self.det_fps = 1.0 / max(time.time() - t0, 1e-3)   # 추론 1회 소요시간의 역수
```

**추론 주기가 아니라 "한 번이 얼마나 빨랐나"** 다. 92.7 은 1회가 10.8ms 걸렸다는 뜻이고,
실제 추론율은 `DET_HZ=4` 니까 **4 Hz** 다. 관제는 **실제의 23배**를 보여준다. 조작자가
"AI 가 92fps 로 돈다"고 읽는다.

### 왜 개명이 최선인가
지금 값이 **이미 소요시간의 역수**라, 로봇은 나눗셈 한 번을 빼면 끝이다. 그리고 조작자에게
"10.8ms"가 "92.7fps"보다 쓸모 있다 — 추론이 프레임 예산 안에 드는지를 바로 답한다.

### 버린 대안
- **(a) 로봇이 실제 추론 주기를 계산해 보낸다** — 코드가 늘고, 무엇보다 그 값은 `DET_HZ`
  설정값과 같아서 **정보가 없다**. 이미 아는 숫자를 텔레메트리로 실어 보내는 셈이다.
- **(b) 둘 다 보낸다** — 필드가 늘고 조작자가 어느 쪽을 봐야 하는지 헷갈린다.

## 5. `captureTs` 를 서버 DTO 에 선언

### 무엇을
`RobotPacket` 에 한 줄:

```java
/** 프레임 촬영 시각. epoch seconds, ms 정밀도 (예: 1786518905.549). */
private Double captureTs;
```

### 왜
**로봇은 2026-08-12 부터 이미 보내고 있다.** 그런데 `RobotPacket` 에 필드가 없어서
`@JsonIgnoreProperties(ignoreUnknown = true)` 가 조용히 버리고, 관제로 나가는 payload 는 그
객체를 재직렬화한 것이므로 FE 까지 도달하지 않는다.

**같은 함정에 걸린 전례가 두 건 기록돼 있다** — `orinPower`(S15P11E101-814),
`readiness`(S15P11E101-869: 2026-08-08 부터 보냈지만 서버에서 통째로 버려져 순찰 시작 게이트가
값을 한 번도 못 받았다). 이번이 세 번째다.

### 무엇에 쓰나
- **이벤트 클립 절단 기준** — 서버 측 절단으로 가면 자를 기준이 화재 확정 시각이다.
  도착 시각으로 자르면 안 된다(송신기가 링크가 느릴 때 프레임을 건너뛰므로 도착 간격 ≠ 촬영 간격,
  그 차이에 상한이 없다).
- **홉별 지연 측정** — "지연이 로봇→AWS 인가 AWS→브라우저인가"를 추측 없이 답한다.

### 버린 대안
- **기존 `timestamp` 재사용** — `Long`, **초 단위**다. 30fps 에서 30장이 같은 값을 갖는다.
  프레임 정렬에 못 쓴다. 참고로 `docs/architecture_and_api_spec.md:170` 의 VIDEO_FRAME 예시에는
  `timestamp` 가 적혀 있는데 **로봇은 그 필드를 실제로 보내지 않는다** — 문서만 존재한다.
  `docs/backend_api_specification.md:301` 쪽에는 아예 없어 두 문서가 서로 다르다. 이 두 곳도
  같이 갱신해야 한다.

## 각주 — HLS 전환 제안이 채택되면 (2026-08-12, 미승인)

레인 A 가 영상을 `ORINCAR_VIDEO_TRANSPORT=off` + nginx 정적 HLS 로 옮기는 안을 제안했다.
아직 정본(`설계_2026-08-12_무인사이클_기동설계.md`)에 반영되지 않았으므로 이 문서는 정본
기준으로 썼다. 채택되면 위 항목이 이렇게 바뀐다.

| 항목 | HLS 채택 시 |
|---|---|
| 3 검출 박스 | **안 A 가 불가능해진다** — HLS 세그먼트에 per-frame 메타데이터를 실을 수 없다. 안 B 가 취향이 아니라 필연이 된다 |
| 5 `captureTs` | 계속 필요. 용도가 "클립 절단 기준"에서 "박스를 영상 타임라인에 맞추는 기준"으로 옮겨간다 |
| 별건 B-5 | **자동 해소** — HLS 세그먼트가 이미 녹화다. 이벤트 시각 주변 세그먼트를 보관하면 클립이 된다. 4개 대체안 택1 자체가 사라진다 |
| 신설 | 영상 채널이 STOMP 를 떠나는 것 자체가 계약 변경이다 — FE 의 `/topic/video/{robotId}` 구독이 없어진다 |

🔴 채택 전에 답이 필요한 두 가지(레인 B 가 제기):
1. **HLS 를 어디서 만드나** — HLS 는 H.264 필수이고 이 Orin 에는 NVENC 가 없다. 로봇에서
   x264 로 인코딩하면 CPU 113.95% 를 먹어 MJPEG 로 도망친 자리로 돌아간다. 단 그 수치는
   **절반 클럭에서 측정된 것**이라 MAXN 에서는 다를 수 있다 — 재측정이 선행이다.
2. **수동조종을 유지하나** — 표준 HLS 는 6초 세그먼트 × 3 버퍼로 **18~30초** 지연이 구조적으로
   생긴다. `LiveSimBridge` 에 WASD 수동조종(데드맨 0.4초, 100ms 재전송)이 있는데 18초 지연
   화면으로는 운전이 불가능하다. 유지하려면 LL-HLS 가 필수고, 그건 "표준 정적 파일"보다
   손이 더 간다(파트 퍼블리싱 + nginx `EXT-X-PART` + hls.js 설정).

## 합의 체크리스트

레인 A 는 항목별로 답만 주면 된다.

- [ ] **1** `status` 값 11개 승인 (또는 목록 수정)
- [ ] **2** `EVENT_SYSTEM` 방송 + `severity` 3등급 승인
- [ ] **3** 검출 박스 — **안 A(프레임 동봉) / 안 B(별도 메시지, 권장)** 중 택1
- [ ] **4** `inferenceFps` → `inferenceMs` 개명 승인
- [ ] **5** `captureTs` DTO 선언 확인
- [ ] **별건** B-5 정본 확정

승인되면 레인 B 는 서버(방송·DTO)와 FE(표시·오버레이)를 먼저 만들고, 로봇 쪽 발행은 레인 A 가
§10 순서에 맞춰 붙이면 된다. **FE 는 모르는 값을 원문 표시하도록 만들 것이므로, 로봇이 나중에
붙어도 중간 상태에서 화면이 깨지지 않는다.**
