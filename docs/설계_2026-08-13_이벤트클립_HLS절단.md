# 사건 클립을 HLS 세그먼트에서 자른다 (2026-08-13)

> 요구: "과열과 화재 알람 시 그 영상을 찍어 보내주는 걸 보자. 지금은 웹사이트에서 아무것도 안 보인다."

## 1. 진단 — 재생기와 선반은 있고, **만드는 사람이 없다**

| 층 | 상태 |
|---|---|
| BE `video` 패키지 | ✅ 완성 — 등록·멀티파트 업로드·목록·상세·**Range 스트리밍**·썸네일 + `GET /api/events/{eventId}/video` |
| FE `EventDetailModal` + `live/videos.ts` | ✅ 완성 — 상세에서 목록·썸네일·재생까지 |
| 클립을 **만들어 등록하는 것** | ❌ 없음. `/api/videos/upload` 를 부르는 코드가 아무 데도 없다 |

화면이 빈 이유는 UI 결함이 아니라 **`video_clips` 에 행이 하나도 없어서**다.
그래서 이번 작업은 FE 변경이 **0** 이다.

## 2. 생산자 후보가 셋이었고 둘이 죽어 있다

### 안 1 — 로봇이 녹화해 올린다 (원래 설계, S15P11E101-588)
서버는 **지금도** 이벤트 저장 직후 `EVENT_SAVED` 로 `eventId` 를 로봇에 회신한다
(`EventLogService.notifyRobotEventSaved`). 로봇 `event_clip_pipeline.py` 가 그것을 받아
자기 클립을 올리는 구조였다.

**죽은 이유**: 그 파이프라인은 `h264_encoder` 가 만든 세그먼트·매니페스트에서 잘라낸다.
2026-08-11 에 MJPEG 패스스루로 전환하면서 **입력이 끊겼다**. 코드는 멀쩡하지만 재료가 없다.
로봇 README 의 표현대로 "지우지 않고 연결만 끊어 둔" 상태다.

**버리지 않았다** — 이 안이 되살아나도 이번 구현과 **충돌하지 않는다**. `video_clips.event_id`
에 여러 행이 붙을 수 있고 관제는 목록으로 보여 준다. 둘 다 있으면 로봇 원본(FHD)과
서버 절단본(HLS 10fps)을 함께 갖게 된다.

### 안 2 — 서버가 `VIDEO_FRAME` 을 받아 자른다 (2026-08-12 결정)
"로봇은 녹화하지 않는다. 서버가 받은 스트림에서 자른다"로 정했고, 그래서 프레임에
`captureTs` 까지 추가했다(도착 시각이 아니라 촬영 시각으로 정렬해야 하므로).

**죽은 이유**: 전제가 "프레임이 Spring 에 도착한다"였는데, 그 뒤 영상이 HLS 로 우회하고
로봇이 `ORINCAR_VIDEO_TRANSPORT=off` 가 되었다. **서버는 프레임을 더 이상 보지 못한다.**
결정 하루 만에 전제가 무너졌다.

### 안 3 — HLS 세그먼트에서 자른다 (**채택**)
재료가 이미 디스크에 있다. 새로 녹화하지 않는다.

## 3. 왜 세그먼트를 신뢰할 수 있나 (2026-08-13 실측)

| 항목 | 값 | 왜 중요한가 |
|---|---|---|
| 세그먼트 | `/var/www/hls/live*.ts`, 2초 (`-hls_time 2`) | 절단 단위 |
| 🔑 삭제 정책 | `-hls_flags omit_endlist+temp_file` — **`delete_segments` 없음** | ffmpeg 이 지우지 않는다 |
| 실제 보존 | `orincar-hls-prune.timer` 5분 주기, **15분 롤링** (실측 191개 / 57MB) | **과거를 자를 수 있다.** `hls_list_size 6`(12초)만 보고 판단하면 안 된다 |
| 시계 차이 | 로봇 ↔ AWS **1초 이내** (동시측정 `1786548813` / `1786548812`) | 로봇이 확정한 시각으로 세그먼트를 고를 수 있다 |
| 디스크 | 208GB 여유 (33% 사용) | 15분 보관·클립 축적에 여유 |

`captureTs` 로 풀려던 정렬 문제(안 2)가 여기서는 **애초에 생기지 않는다** — 세그먼트는
같은 기계에서 벽시계 순서대로 쌓이고, mtime 이 곧 그 세그먼트가 닫힌 시각이다.

## 4. 어디서 자를 것인가 — 상자 안 vs 밖

BE 는 Docker 컨테이너(`bbiyong-server`)다. 마운트가 `/opt/bbiyong/data → /app/data` **하나뿐**이라
세그먼트를 볼 수 없고, 컨테이너에 **ffmpeg 도 없다**.

| | 안 A (**채택**) | 안 B (버림) |
|---|---|---|
| 방식 | 컨테이너에 ffmpeg 추가 + `/var/www/hls` 를 `:ro` 마운트 | 호스트에 에이전트를 두고 BE 가 요청 파일을 떨군다 |
| 코드 | Spring `@EventListener` 하나 | 저장소 밖 프로세스 + **두 번째 계약**(요청 파일 형식·업로드 토큰) |
| 이력 | 전부 git 안 | 에이전트가 git 밖 → 로봇과 같은 "이력 없는 코드" 문제 재생산 |
| 대가 | 이미지 +약 80MB, 재배포 필요 | 이미지 변경 없음 |

안 B 를 버린 결정적 이유는 크기가 아니라 **계약이 하나 더 생긴다**는 점이다. 이 프로젝트에서
가장 비싸게 물린 실패들이 계약 불일치(서버 DTO 필드 누락 3건, `patrol_running` 항상 거짓)였다.

`:ro` 마운트라 서버가 라이브 송출 파일을 **망칠 수 없다**. 절단은 `-c copy` 스트림 복사라
재인코딩이 없고 CPU 를 거의 쓰지 않는다.

## 5. 🔴 지연 실행이 이 설계의 본질이다

이벤트가 확정된 **그 순간에는 사건 이후 구간의 세그먼트가 아직 존재하지 않는다.**
즉시 자르면 뒤가 잘린 클립이 나온다. 그래서 `post + 4초` 를 기다린 뒤 자른다.

4초의 근거: 사건이 세그먼트 중간에 걸리면 그 세그먼트는 최대 2초 뒤에 닫히고,
ffmpeg 이 `temp_file` 로 쓰고 rename 하는 시간이 더 필요하다.

전용 단일 스레드를 쓴다(공용 풀 아님):
- 9초 대기 동안 풀 스레드를 붙잡으면 **경보 처리와 경합**한다
- 단일 스레드면 ffmpeg 프로세스가 동시에 여러 개 뜨지 않는다

## 7. 곁들여 고친 것 — 저장 경로가 컨테이너 내부였다

`bbiyong.video.storage-dir` 기본값이 `video-store`(상대경로)라 실제로 `/app/video-store`,
즉 **컨테이너 내부**에 저장된다. 마운트가 아니다.

컨테이너를 다시 만들면 파일만 사라지고 `video_clips` 행은 DB 에 남는다 → 관제에서
**목록에는 보이는데 재생만 실패**하는, 가장 알아채기 어려운 형태의 손실이 된다.
지금까지 클립이 하나도 없었으므로 실제 손실은 없었다.

→ compose 에서 `BBIYONG_VIDEO_STORAGE_DIR=/app/data/video-store` 로 바인드 마운트 안으로 옮겼다.
권한 확인: `/opt/bbiyong/data` 는 uid 999(컨테이너의 `spring`) 소유이고 실제 쓰기 성공,
`/var/www/hls` 는 `o+rx` 라 같은 uid 로 읽을 수 있다.

## 8. 미결 · 위험

- 🔴 **실사 미검증** — 실제 화재/과열로 클립이 생기는 것은 아직 확인하지 못했다.
  배포 후 열원으로 과열을 만들어 `이벤트 클립 등록:` 로그와 관제 상세 화면을 함께 봐야 한다.
- 🔴 **HLS 는 인증이 없다**(기존 사안). 클립은 인증된 `/api/videos/{id}/stream` 으로만 나가지만,
  같은 영상의 라이브는 `https://…/hls/live.m3u8` 로 누구나 볼 수 있다.
- ⚠️ **클립 디스크가 무한히 는다.** `video_clips` 에 보존 정책이 없다. 사건당 약 15초 ×
  1200kbps ≈ 2MB 라 당장은 문제가 아니지만, 정리 주기를 정해야 한다.
- ⚠️ 세그먼트가 없으면(카메라·터널 정지, 또는 15분이 지나 prune 됨) **클립을 만들지 않고
  경고만 남긴다.** 빈 행을 등록하면 관제에 재생 안 되는 항목이 남기 때문이다.
- ⚠️ `saveAndFlush` 는 flush 이지 commit 이 아니다. 저장 트랜잭션이 나중에 롤백되면
  존재하지 않는 `eventId` 를 가리키는 클립이 남을 수 있다. `video_clips.event_id` 에 FK 가
  없어 정합성 오류로 번지지는 않지만, 고아 행이 된다.
- ⚠️ 클립은 HLS 화질(10fps · 1200kbps · H.264)이다. 로봇 원본(FHD 30fps)이 아니다.
  원본 화질이 필요하면 안 1(로봇 업로드)을 되살려야 한다 — 둘은 공존할 수 있다.
