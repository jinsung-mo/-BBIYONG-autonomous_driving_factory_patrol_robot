# 삐용 (BBIYONG) - Jira 및 Git 협업 컨벤션 가이드

본 문서는 팀 E101의 원활한 협업과 체계적인 일정 관리를 위한 Jira(지라) 티켓 및 Git(깃) 연동, 브랜치 전략 컨벤션 규칙을 정의합니다. 모든 팀원은 작업 시작 전 본 규칙을 숙지하고 일치된 컨벤션을 준수합니다.

---

## 1. Jira 협업 3대 핵심 규칙

1. **No Ticket, No Commit (티켓 없이는 코드도 없다)**
   - 모든 개발 작업은 지라 티켓 생성부터 시작하며, 코드 커밋과 브랜치에 항상 지라 티켓 번호를 남깁니다.
2. **Task Granularity (티켓은 1~2일 단위로 쪼개기)**
   - 완료까지 3일 이상 걸리는 대형 티켓은 지양합니다. 1~2일 내에 완료할 수 있는 세부 태스크 단위로 작게 쪼개어 발행해야 진행률이 투명하게 보입니다.
3. **Real-time Status Update (실시간 보드 상태 갱신)**
   - 작업을 시작할 때 티켓을 **`진행 중(In Progress)`**으로 이동시킵니다.
   - 코드 리뷰 요청(PR/MR) 시 **`리뷰 중(In Review)`**, 최종 머지 완료 시 **`완료(Done)`**로 즉시 이동시켜 팀원들이 서로의 진행 상황을 실시간으로 알 수 있게 합니다.

---

## 2. Jira 티켓 위계 및 구조 (Hierarchy)

팀 E101은 프로젝트 복잡도를 낮추고 명확한 진행 상황을 추적하기 위해 **`Epic ➔ Story ➔ Task`**의 3단계 위계 구조를 사용합니다. **하위 작업(Sub-task) 기능은 사용하지 않습니다.**

* **에픽 (Epic)**: 기존에 생성된 큰 단위의 에픽(예: 기획/설계, 웹 프론트엔드 개발 등)을 그대로 활용하여 분류합니다.
* **스토리 (Story)**: 사용자 관점의 큰 서비스/기능 단위로 작성합니다.
  * *예시*: `회원 관리`, `로봇 제어 대시보드 UI`, `영상 스트리밍 서버 구축`
* **태스크 (Task)**: 스토리를 완료하기 위한 구체적이고 쪼개진 개발 항목 단위로 작성합니다 (1~2일 내 완료 가능한 수준).
  * *예시*: `스프링 시큐리티 기반 JWT 로그인 API 구현`, `로봇 제어 조이스틱 컴포넌트 마크업`
* **하위 작업 (Sub-task) 제한**: 작업 추적의 단순화와 일관성을 위해 Jira 고유의 하위 작업(Sub-task) 티켓 타입은 생성하지 않으며, 모든 세부 업무는 개별 `Task` 티켓으로 발급합니다.

## 3. Jira 티켓 제목(Summary) 규칙

티켓 제목은 한눈에 작업 성격과 대상 영역을 파악할 수 있도록 **`[유형][모듈] 작업 내용 요약`** 형식(가장 권장)으로 작성합니다. 작업 유형과 대상 영역을 함께 적어주면 구체성이 높아집니다.

* **유형**: `Feat`, `Fix`, `Docs`, `Design`, `Refactor`, `Chore`, `Test` 등
* **모듈**: `FE`, `BE`, `AI`, `Robot`, `System`, `Docs` 등

### 3.1 작성 예시
* **`[Feat][BE] 회원가입 API 구현`**
* **`[Fix][FE] 버튼 클릭 이벤트 미동작 수정`**
* **`[Docs][BE] 관제 서버 API 명세서 작성`**
* **`[Chore][System] SQLite JPA 라이브러리 추가`**

## 4. Jira 티켓 본문(Description) 작성 템플릿

작업 상세 내역과 완료 기준을 투명하게 공유하기 위해, 티켓 생성 시 아래 **3단계 템플릿(이모티콘 제외)**을 적용하여 작성합니다. (이 템플릿은 GitLab MR 작성 시에도 자동으로 채워집니다.)

Jira Cloud의 Wiki Markup 파서와의 호환성(API 등록 시 `#` 기호가 Numbered List `1. a. i.`로 깨지는 현상 및 리스트 중첩 방지)을 위해, 리스트 기호는 하이픈 대신 **별표(`*`)** 사용을 권장합니다.

```markdown
### 개요 (Context)
(이 작업을 진행하게 된 배경이나 목적을 1~2줄로 서술합니다.)

### 작업 상세 내용 (To-Do)
* [ ] (구체적인 작업 항목 목록)

### 완료 기준 (Definition of Done)
* [ ] (해당 티켓 완료를 검증할 수 있는 테스트 및 확인 조건)
```

> [!IMPORTANT]
> **API/스크립트를 통한 프로그램적 티켓 생성 시 주의사항:**
> Jira REST API v2를 통해 본문(Description) 문자열을 직접 전송할 때 마크다운의 `###` 기호를 그대로 쓰면, 지라의 Wiki Markup 파서가 이를 **3단계 중첩 순서 목록(1. a. i.)**으로 오인하여 깨지게 됩니다. 
> 따라서 API나 Python 스크립트로 티켓을 생성 및 업데이트할 때는 아래와 같이 변환하여 전송해야 지라에서 정상적으로 보입니다:
> - `### 제목` ➔ `h3. 제목`
> - `- [ ]` ➔ `* [ ]`
> - `- [x]` ➔ `* [x]`

## 5. Git ↔ Jira 연동 규칙 및 브랜치 전략

Jira 프로젝트와 GitLab/GitHub을 연동하여 작업 이력을 완벽하게 추적(Traceability)하기 위한 커밋 및 브랜치 명명법입니다.

### 5.1 브랜치 명명 컨벤션 (Branch Name)
* **파트별 공통 메인 브랜치 (보호됨)**: `fe/main`, `be_system/main`, `be_robot/main`, `ai/main`
* **기능 개발 브랜치 생성 규칙**: `[접두사]/[Jira티켓번호]-[간단한작업명]`
  * *예시*: **`feat/S15P11E101-144-login`**

### 5.2 커밋 메시지 컨벤션 (Commit Message)
* **메시지 작성 규칙**: `[Jira티켓번호] 접두사: 커밋 메시지 내용`
  * 대괄호 `[Jira티켓번호]`를 맨 앞에 정확히 적어야 지라 티켓에 해당 커밋 코드가 자동으로 기록됩니다.
  * *예시*: **`[S15P11E101-144] feat: 스프링 시큐리티 기반 JWT 로그인 API 구현`**

## 6. 실무 개발 및 머지(Merge) 워크플로우

### 6.1 로컬 작업 시작
반드시 본인 파트의 공통 메인 브랜치를 최신화한 후 분기합니다.
```bash
git checkout be_system/main
git pull origin be_system/main
git checkout -b feat/S15P11E101-144-login
```

### 6.2 작업 완료 후 푸시 및 MR 요청
* **Push**: 개발 완료 후 개인 브랜치를 push합니다. (동시 푸시 설정이 되어 있어 GitLab과 GitHub에 동시에 올라갑니다.)
  ```bash
  git push origin feat/S15P11E101-144-login
  ```
* **Merge Request (Target 브랜치 주의)**:
  - Source: `feat/S15P11E101-144-login`
  - Target: **`be_system/main`** (최종 `main`이 아닌, 본인 파트의 브랜치로 머지합니다!)
  - 웹페이지에 연동된 템플릿의 체크리스트를 채우고 파트원 승인을 얻어 병합합니다.

### 6.3 최종 배포 통합
스프린트가 끝나거나 배포 시점에 각 파트의 `*/main` 브랜치들을 최종 상위 브랜치인 **`main`** 브랜치로 최종 병합합니다.
